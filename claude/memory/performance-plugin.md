`~/.config/omarchy/plugins/io.github.rezwoan.performance/` (display name **PredatorSense**) — a bar-widget plugin for `omarchy-shell` (Quickshell/QML) ported from an old walker-menu extension. General tab: one unified **Profile** selector (Ultra Saver / Saver / Balanced / Performance / Ultra Performance / Custom — Custom is a passive indicator, not a settable preset, shown whenever a raw control has been hand-tuned since the last named preset) plus CPU/GPU/battery/fan/session controls, with the old separate Power Profile + Thermal Profile rows tucked behind a small gear (⚙) button. Keyboard tab: brightness/color/effects for the Predator's 4-zone RGB, including a "Profile" color swatch and a "Match Predator mode" quick action that both track the live mode color. Bar icon and panel header show the Acer Predator claw logo (`assets/predator-mask.png`), recolored live via `QtQuick.Effects.MultiEffect{colorization}` based on active mode: green=saver family, magenta=performance family, blue=balanced. This is personal tooling synced into [[omarchy-setup-repo]], not a published marketplace plugin — an earlier session built out full marketplace scaffolding (separate public repo, CONTRIBUTING.md, issue templates, NOTICE.md trademark disclaimer) before the user decided against publishing; that scaffolding was removed from the live plugin dir since it only makes sense for a standalone public repo. See [[machine-hardware-setup]].

**v2.0.0** added a third tab, **Telemetry**: live CPU%/RAM/CPU-temp/GPU-util/GPU-temp/GPU-power stat tiles (color-coded via a shared green→amber→orange→red threshold ramp), a ~2.5-min rolling CPU/GPU-load sparkline (`Canvas`, `onPaint`, manual `requestPaint()` on new data — no shared gauge/sparkline component exists anywhere in `qs.Ui`/`qs.Commons`, confirmed via grep, so this is hand-rolled), GPU hardware info, and a capped GPU-process list — plus a **software fan curve** (draggable temp→speed `Canvas` editor). Telemetry sources, all unprivileged: CPU% from two `/proc/stat` samples (delta against a state file, avoids a blocking sleep); RAM from `/proc/meminfo`'s `MemTotal - MemAvailable`; CPU temp by matching `thermal_zone*/type` against `x86_pkg_temp`/`TCPU`/`TCPU_PCI` **by name, not zone index** (zone numbering isn't stable across boots), falling back to the `coretemp` hwmon chip; fan RPM from the `acer` hwmon chip (also matched by name); GPU everything (util/VRAM/temp/power/clocks/driver/VBIOS/PCIe-link) from one `nvidia-smi --query-gpu=...,name,driver_version,vbios_version,pcie.link.gen.current,pcie.link.width.current --format=csv,noheader,nounits` call — no `lspci` needed. `nvidia-smi` returns the literal string `"[N/A]"` for fields a given GPU doesn't report (e.g. `power.limit` on this laptop) — a `sanitize_num()` helper rejects anything that isn't a bare number, coercing it to `-1`, the shared "not reported" sentinel every `Model.js` formatter (`fmtTemp`/`fmtPct`/`fmtWatts`/etc.) checks for. `status.sh`'s final JSON assembly moved from a giant `printf` to `jq -n` once field count grew past ~25 and nested JSON (history, process list) needed embedding — manual `printf`-based JSON escaping doesn't scale past a certain field count/nesting depth.

The **fan curve daemon** (`fancurve.sh`) is a `systemd --user` unit (`omarchy-perf-fancurve.service`), not a disowned bash loop — Omarchy's own migration history (`/usr/share/omarchy/migrations/1785167800.sh`) documents moving *away* from a disowned background process for fcitx5, citing the exact orphan-process-nobody-can-stop failure mode. The daemon itself is fully unprivileged: it polls temp every ~5s and calls the *existing* `sudo -n omarchy-perf-helper fan <pct>` path — no new sudoers/polkit surface at all. Installing the *unit* also needs no root (writing to `~/.config/systemd/user/` is a plain user operation), so the whole feature toggles on/off via `systemctl --user enable/disable --now`, wired directly from the panel with no setup.sh re-run needed. Safety: `ExecStopPost=-sudo -n omarchy-perf-helper fan auto` on the unit, backed up by an in-script `trap ... EXIT`, so a crash/stop/disable always reverts to auto fan — verified live by running the daemon under `timeout --signal=TERM` and confirming `fan_speed` read back `"0,0"` after the kill. Curve points persist to `~/.config/omarchy/predatorsense-fancurve.json` (a plain array of `{temp,speed}`, linear-interpolated in bash via one `jq`+`awk` pass per point — small point count makes this fine despite not being the most efficient approach).

Privileged writes go through `sudo -n /usr/local/bin/omarchy-perf-helper <verb>` — a root-owned, verb-whitelisted script installed by the plugin's own `setup.sh`, authorized via a NOPASSWD sudoers rule scoped to just that binary (`/etc/sudoers.d/omarchy-perf-helper`). One real password prompt ever (the "Enable privileged controls" button, via `pkexec bash setup.sh`); every other control calls `sudo -n` and fails closed silently if the rule isn't installed yet. A polkit-based model (scoped `.policy` action, `pkexec` per click) was tried in between and reverted — it worked but re-prompted with a real auth dialog periodically (`auth_admin_keep` only caches for a few minutes), which the user explicitly didn't want ("no popup with any password box").

**Hard lessons (re-check these if a future plugin edit "does nothing" again):**
- `bar.shellQuote()` **does not exist**, despite `shell/plugins/bar/README.md` documenting it as a `bar` API. The real function is `Util.shellQuote()` from `qs.Commons`. Calling `root.bar.shellQuote(...)` throws a silent QML TypeError (visible only in `journalctl --user -t omarchy-shell`) — every click did nothing and left no visible error. Always grep the actual shell source (`/usr/share/omarchy/shell/`) for real usages before trusting a plugin README's API list.
- **Editing an already-placed bar-widget plugin's QML does NOT reliably hot-reload**, even though `shell/plugins/README.md` claims file saves auto-reload. `omarchy-shell shell rescanPlugins` didn't help either. Only `omarchy restart shell` (full quickshell process restart, confirmed via a new PID) reliably picks up changes to a widget already sitting in the bar. Verify any layout/logic change with a real restart + `grim` screenshot, not by trusting the log's "Local plugin changed, reloading" line.
- `ButtonGroup` is a plain `Row` — it does **not wrap**. A row with more than ~4 options (e.g. this machine's 5 `platform_profile` choices, or the 6-option Profile selector, or 10 keyboard-color swatches) silently overflows the panel's right edge. Use a fixed-column `Grid` (like the first-party `monitor` panel's scale-preset row) instead — plain `Flow` was tried first and, unexplained, did not wrap either.
- `qmllint` (`/usr/lib/qt6/bin/qmllint`, not on PATH) can't resolve the `qs.Ui`/`qs.Commons` virtual import scheme at all — even linting a known-good first-party file produces the same cascade of "not found" warnings. That noise is expected; only trust it for real syntax errors (brace/paren mismatches), not import-resolution warnings.
- **The `linuwu_sense` driver's `fan_speed` sysfs node expects `"cpu,gpu"` (e.g. `"50,50"`, or `"0,0"` for auto)** — see `predator_fan_speed_store`/`_show` in `/usr/src/linuwu-sense-*/src/linuwu_sense.c`. Writing a bare number (what the helper originally did) is silently rejected with `-EINVAL`; the fan control just did nothing with no visible error. Read it back the same way (`raw%%,*` for the first field) — don't assume a single-value format just because the control only exposes one slider.
- **The physical Predator/turbo button IS distinguishable from Fn+F6 at the evdev level on this hardware** — confirmed via a live raw evdev capture (open every `/dev/input/eventN`, print `EV_KEY` events with device name, ask the user to press each key in turn with a pause between). The Predator button fires *only* evdev code 148 (`KEY_PROG1`) on the "AT Translated Set 2 keyboard" device; Fn+F6 fires on entirely different devices ("Video Bus" code 225 = `KEY_BRIGHTNESSUP`, "Acer WMI hotkeys" code 240 = `KEY_UNKNOWN`) and never touches code 148. An earlier session wrongly concluded these collided — likely from trusting `hyprctl binds -j`'s `key`/`keycode` fields, which show empty (`""`/`0`) for **every** `code:`-syntax bind, including known-working stock ones (verified by comparing against `SUPER + code:20` from `tiling.lua`) — that field simply isn't populated for keycode-based binds, it's not evidence the bind failed. Bound in Hyprland Lua as `o.bind("code:156", ...)` (156 = evdev 148 + 8, Hyprland's X11 keycode offset) with **no modifier prefix** — bare `code:NNN` binds fine standalone, matching plain keysym binds like `XF86MonBrightnessUp` (modmask 0). The driver's kernel-level `WMID_GAMING_TURBO_KEY_EVENT` path (a *different* physical key/behavior on some models — toggles turbo or cycles thermal profile entirely in-kernel via `acer_toggle_turbo()`, logging `"pressed turbo button - N"` but emitting zero evdev event) was a dead end for *this* button on *this* firmware — don't assume that's the mechanism without live-testing first.
- **`hyprctl dispatch exec "[workspace N silent] cmd"` — the classic bracket-tag mini-DSL — is ALSO rejected on this Lua-parsed Hyprland config**, same failure family as `hyprctl keyword` below: `hyprctl` tries to parse the whole dispatch argument as Lua source and chokes on `[workspace N silent]` ("']' expected near 'N'"). Found while debugging why session-restore (`local-bin/omarchy-perf-session-restore`, part of [[omarchy-setup-repo]]) never actually relaunched anything — the error was silently swallowed by `>/dev/null 2>&1`. Fix: use the Lua dispatch API directly — `hyprctl eval 'hl.exec_cmd("cmd", { workspace = "N silent", float = true })'`. Confirmed via direct testing: `workspace` accepts `"N"` or `"N silent"` (the modifier is part of the same string, not a separate key — a bare `silent = true` key errors with "unknown effect 'silent'"), `float` is a plain boolean. This is the third distinct instance of "the classic hyprctl string-tag syntax doesn't survive Lua parsing" in this one machine's config (after `hyprctl keyword monitor` and plain `hyprctl dispatch <name> <args>` for binds) — worth assuming *any* hyprctl call using bracket-tag or space-separated legacy syntax needs the `hl.*` Lua API instead, on any Lua-configured Hyprland.
- **`hyprctl keyword monitor` is rejected outright on a Lua-parsed Hyprland config** ("keyword can't work with non-legacy parsers"). Refresh-rate changes must go through `hyprctl eval` + the `hl.monitor({ output, mode, position, scale })` Lua API instead. `position` only accepts `"auto"` cleanly here — an explicit `"x,y"` string errors on the position field (confirmed by testing both). A third-party plugin (`moneytosms/omarchy-asus`) independently hit and solved the exact same issue the same way — good outside confirmation this is the right fix, not a workaround specific to this machine.
- **`grim -g` geometry syntax is `"x,y widthxheight"`** — comma between x/y, lowercase `x` between width/height. Swapping them (`"x,y width,height"`) fails with "invalid geometry" (a clear error) rather than silently misbehaving, which is at least easy to catch.
- **QML `Grid` sizes each column to its widest cell's natural (implicit) width — it does not evenly divide `width: parent.width` across columns.** Adding an icon (`iconText`) to `Button`s in a 3-column `Grid` widened them enough that the total row exceeded the panel's width; since `Grid` has no wrap/scroll fallback, the last column silently overflowed past the visible panel edge (only caught by an actual screenshot — QML logged zero errors/warnings). Fix: either give each cell an explicit `width: (grid.width - spacing) / columns` binding, or drop to fewer columns so natural sizing has more room. Don't trust "no QML errors after restart" as proof a layout looks right — errors and layout correctness are orthogonal; a real (even cropped) screenshot is the only way to catch this class of bug.
- **`jq` is a hard dependency of the `omarchy` package itself** (confirmed via `pacman -Qi jq` → `Required By: omarchy`), safe to rely on unconditionally in any Omarchy plugin's shell scripts — no need to gate every `jq` call behind `command -v jq`.
- **Neither sibling laptop-control plugin actually achieves "zero manual install" for free** (checked directly, not assumed, when the user asked why this plugin isn't as seamless): `moneytosms/omarchy-asus` piggybacks on `asusctl`/`asusd`, a vendor package that ships its own root D-Bus daemon + polkit policy at `pacman -S asusctl` time — a real one-time privileged step, just relocated outside the plugin. `ucmz851/omagpu` has no scoped polkit policy at all (confirmed: no `.policy`/`.rules` file in its repo) — its own README admits tuning "prompts through standard desktop PolicyKit authentication," i.e. a real popup on every privileged action. Omarchy's `omarchy-plugin-add` CLI also has zero install-hook mechanism (grepped the actual script — it only stages files and registers the manifest). There is no Acer equivalent to `asusd` to piggyback on. Conclusion: this plugin's one-real-prompt-then-`sudo -n`-forever model is the better tradeoff of the three real options, not a gap to close.
